# Tools

The FrameOn MCP server exposes **20 tools**: 13 read-only and 7 that write.
The descriptions below are the ones the server actually advertises in
`tools/list` — they are read from the live catalogue, not hand-copied.

Every tool except `list_skills` and `get_skill` takes a `project_id`. Omit it
and the error response lists the projects the credential can reach, so an agent
can recover without a second round-trip to a human.

## Read-only (13)

| Tool | What it does |
| --- | --- |
| `list_tasks` | Lists tasks in one project with optional filters by status, type, priority and free text. Paginated: `limit` caps at 100 and the response carries `has_more` and `next_page` — a backlog you read only to page 1 is a backlog you read wrong. Call this before `create_task` to find the parent an item belongs under, and before `update_task` when you do not have the id. Omit `project_id` once and the error hands you every project this token can reach. |
| `get_task` | Returns one task in full: description, dates, assignee, labels, status and parent. Accepts either the human id (LAB-42) or the UUID. Use it when a row from `list_tasks` needs the detail behind it. Do not loop it over a whole backlog — filter with `list_tasks` instead, which is one call rather than fifty. |
| `get_task_stats` | Aggregate counts for one project: totals by status, by type and by priority, plus what is overdue. This answers "how is this project doing" in a single call, instead of paging through `list_tasks` and counting by hand. It reports the project as a whole — for numbers broken down per epic, `get_project_structure` is the only tool that has them. |
| `get_project_team` | Lists the people on this project with their ids: explicit members when the project restricts visibility, otherwise the distinct assignees of its tasks. Use the returned id as `assignee_id` in `create_task` or `update_task` — never guess an id, and never assign work to someone this tool did not return. Read-only, one project per call. |
| `get_project_structure` | Returns the project hierarchy: every epic with its children, counts and progress. Pass `include_tasks=true` when you need the level below stories. This is the ONLY tool that reports per-epic numbers. Call it before `create_task` and parent the new work under the epic it belongs to — a new top-level task is a decision, not a default. What you see here is how this team actually organises work, which may not follow the epic > story > task > subtask convention: hierarchy in FrameOn is free, any task type may parent any other, and an unusual shape is a choice the team made, not an error for you to correct. |
| `search_documents` | Semantic search over this project Wiki pages and uploaded documents. It matches meaning, not keywords, so give it a question rather than a term. Returns between 1 and 10 excerpts (default 5), never whole pages — when an excerpt looks right, follow up with `get_document_full_content`. Always search before `create_wiki_page`: the point is to extend the team memory, not to duplicate it. |
| `list_documents_brief` | Lists this project's documents and Wiki pages with title and id only, newest first. Cheap to call, and the right way to see what exists before reading anything. It is paginated: the response carries `total` and `has_more`, and you reach older entries by calling again with `page: 2`, `page: 3`, and so on — never treat page 1 as the whole Wiki when `has_more` is true. To find a specific subject, `search_documents` is faster than paging through everything. Feed the id you picked into `get_document_full_content`. |
| `get_document_full_content` | Reads one document or Wiki page in full, by id. Content past 25,000 characters is truncated and the response says so explicitly — when you see that flag, tell the person, instead of reasoning as though you had the whole text. Use it after `search_documents` or `list_documents_brief` pointed at the right page. It is not a way to browse: reading the Wiki page by page burns the context you need for the actual work. |
| `get_project_alerts` | Lists the risk alerts this workspace raised for the project on its own: overdue work, deadlines about to slip, tasks with no movement, no owner or no due date, people overloaded. Read-only, and the fastest way to answer "how is this project doing" with evidence instead of impression — the alerts were computed from the data, not from a summary you wrote. Defaults to active alerts only. Each one carries `type`, `severity`, a human message, and the task it points at when it points at one. Two things worth knowing. The list is filtered by what the token's role is allowed to see, so an empty result means "nothing you can see", not always "nothing exists". And you cannot resolve or dismiss an alert through this connector — that stays with a person in the UI, on purpose. Report what is open and let them decide. |
| `get_time_report` | Time report for the project over the last `periodDays` (default 30, max 365): hours planned versus hours actually logged, the billable split, and the tasks where the two diverge most. Planned counts leaf tasks whose plan overlaps the window; worked counts time entries logged inside it. A null KPI means the other side is missing — it is NOT zero, and reporting it as zero turns "nobody planned this" into "the team overshot by 100%". Use it when someone asks how a period went, before writing any status update. Pair it with `get_project_alerts` for the risk side and `get_task_stats` for the delivery side. |
| `get_project_memory` | Returns everything this project knows about itself as one markdown briefing: decisions taken and why, conventions agreed, what is written in the Wiki, the risks currently open and the work in flight. READ THIS FIRST, before you touch the project's code or answer a question about it. It is the shared memory that replaces the notes file living on one developer's machine — what the last person learned is in here, and it is the difference between continuing the work and rediscovering it. The text is assembled from the workspace's own records and handed to you raw, not summarised by us. Read it yourself and keep what matters. Memories marked confidential are not included, deliberately. The Wiki appears as titles and ids — call `get_document_full_content` on the ones that matter instead of asking for everything at once. When you finish and have learned something the next person would want, write it back with `save_classified_memory`. |
| `list_skills` | Lists the ready-made workflows this workspace knows how to run: diagnosing a project, reporting on a period, breaking scope into tasks, logging your hours, and inheriting or handing over the project's shared memory. Cheap to call, and worth calling once at the start of a session so you know what exists before improvising a sequence of calls. Each entry carries a name, one line of what it is for, and the tools it uses — so you can tell up front whether this token reaches them. A skill is a script for YOU: it says which tools to call, in what order, and what to deliver. Nothing executes on the FrameOn side, and asking for one costs you nothing but the text. Pick a name and call `get_skill`. |
| `get_skill` | Returns the full script of one workflow: the tools to call, the order to call them in, what to look at in each result, and what to hand back at the end. Read it and then run it yourself with your own tools — these are instructions for you, not a job queued on our side. That is the whole design: the workflow costs the workspace nothing to hand you, and the thinking stays with you. The scripts encode things that are easy to get wrong here and expensive to get wrong twice: that a null figure in a report is missing and not zero, that hours are always logged for the token holder and always land unapproved, that the task hierarchy is a recommendation and never a rule to enforce, and that write steps are proposed to the person first and carried out after they agree. Call `list_skills` first if you do not know the names. |

## Write (7)

Write tools appear **only** when the credential carries the `write` scope *and*
the role behind it allows the action. A read-only token does not see them at
all — they are absent from `tools/list`, not present-and-refusing.

| Tool | What it does |
| --- | --- |
| `create_task` | Creates ONE task in a project. Hierarchy in FrameOn is FREE: any task type may parent any other, a subtask may have children, and nothing is ever rejected because of its shape. The usual convention is epic > story > task > subtask, and it is a RECOMMENDATION — suggest it, never enforce it, and follow what the person asks for even when it breaks the convention. Call `get_project_structure` first so the new item lands under the work it belongs to; a new top-level task is a decision, not a default. One call creates one task: to build a breakdown, show it to the person, wait for agreement, then create the items one by one. Take `assignee_id` from `get_project_team`. |
| `update_task` | Changes fields of an existing task: status, priority, assignee, dates, title, description, story points, labels. Send only what actually changes — fields you omit are left untouched. Get the id from `list_tasks` and the `assignee_id` from `get_project_team`. Never mark something done that is not done: status here is what the rest of the team reads to decide what to pick up next. |
| `add_comment` | Adds a comment to a task — the running log of that task history. Progress, what broke, what is still open, and what you actually did belong here, written for the person who picks this up cold next week and not as a recap of your conversation. A comment records what happened; `create_wiki_page` records a decision and its reasoning, which outlives the task. |
| `create_wiki_page` | Creates a Wiki page in the project. Write one when a decision was made and the reasoning would be expensive to reconstruct, when something failed and the next person would repeat it, or when a convention was established that is not visible in the code. Do not write one for something the commit history already says. Search with `search_documents` first. The Wiki through MCP is APPEND-ONLY: you never rewrite someone else page — to correct an earlier one, create a new page that references it. |
| `report_ai_usage` | Report the AI tokens and cost your own agent runtime just spent, so this workspace can show the real cost of a project alongside the human hours. ONLY call this when your runtime hands you actual usage counters from the provider response (input/output token counts). If you do not have measured numbers in front of you, do not call this tool and do not estimate — a guessed number is worse than no number, because it looks like a measurement. Send `task_id` whenever you know which piece of work the spend belongs to: without it the cost lands on the project, or on nothing, and nobody can tell which task was expensive. Send `hours` in the SAME call when you also know how long the person spent on it. Tokens are half of what the work cost; the other half is someone's time, and a project report showing only the token side understates the truth. The entry is always the token holder's, lands unapproved, and a person still approves it in the UI. Deduplication: same session_ref + model + day + task overwrites the previous row instead of adding to it, so resending a run that grew is correct and safe. That guarantee covers the TOKENS only — `hours` creates a new time entry every time, so do not resend a call that already logged them. |
| `log_time` | Logs hours YOU just worked on a task, so the human time and the AI time of a project sit in the same place. The entry is always yours: the person who owns the token. There is no field for a user id in this tool and that is deliberate — logging hours in someone else's name is a billing error that looks like data. The entry lands UNAPPROVED, inside the open timesheet period. A person still submits and approves it in the UI; nothing here skips that. It will be refused, and the refusal is correct, when: the task is already `done` (reopen it first), the work date is more than 90 days in the past or more than 1 day in the future, or the timesheet period covering that date was already submitted or approved. Do not retry a refusal with a different date to make it pass — tell the person what happened. Only log what actually happened. `hours` is decimal: 1.5 is an hour and a half, 0.25 is fifteen minutes. Describe the work in `description` — six months from now the number alone means nothing. |
| `save_classified_memory` | Saves something learned about this project so the NEXT person — or the next session, or another developer's assistant — starts already knowing it. This is the shared memory of the project: what you write here outlives your session and is readable by everyone who can reach the project. Write a memory when a decision was made and the reasoning would be expensive to reconstruct, when something failed and the next person would repeat it, when a convention was agreed that the code does not show, or when a constraint came from outside the code (a client rule, a deadline, a dependency on another team). Do not write what the commit history already says, and do not write your own task list. Use `forceCategory` when you know what it is: `decision` for a choice with a reason, `process` for how something must be done, `fact` for something that is simply true, `context` for background, `preference` for how the team likes to work, `relationship` for who owns or depends on what. Left empty it is classified automatically. It appends — it never edits or replaces an earlier memory. To correct one, save a new memory that says what changed and why. Read the other side with `get_project_memory` at the START of your work, not at the end. |

## Tool annotations

All 20 carry the standard MCP hints (`readOnlyHint`, `destructiveHint`,
`idempotentHint`, `openWorldHint`).

`destructiveHint` is `false` on all seven write tools, and that is a decision
rather than an oversight: none of them deletes, revokes access or sends
anything outward. What they do is append — a task, a comment, a wiki page, a
time entry — or update fields on a record the caller already proved they can
reach. Nothing exposed here removes data. Destructive operations exist in
FrameOn, and are deliberately not part of this surface.

## Skills

`list_skills` and `get_skill` return **text, not execution**. A skill is a
playbook: which tools to call, in what order, what to look at in the result and
what to hand back. The reasoning is done by your model, with your tokens —
nothing runs on the FrameOn side. The same playbooks are also exposed as MCP
prompts, because many clients read one surface and not the other.
